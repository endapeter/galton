# Galton Board Research — Plan & Technical Overview

*Last updated: 2026-08-21*

---

## 1. Research Goals

The project investigates the Galton board as a physical random-process generator, starting from
`problem.txt`:

1. **Baseline phenomenon** — beads dropped on an evenly pegged board produce a binomial
   distribution (the discrete analogue of the normal / CLT outcome).
2. **Distribution shaping** — can *other* distributions be generated by varying board parameters
   (peg size, peg spacing/lattice, bead format/size, coefficient of restitution, funnel width)?
3. **CLT violation** — can the board produce a distribution that does *not* obey the central
   limit theorem in an i.i.d. scenario (heavy tails / infinite variance)? The notes flag the
   **arcsine law** as a target to reproduce and understand ("what is going on in the gaps in the
   arcsine law distribution?").
4. **Vibration** — what happens to the output distribution when the board vibrates? Open sub-
   questions from `notes.txt`: mean free path / mean free time between peg hits; possible
   **resonance** if the vibration frequency matches the peg-bounce frequency.
5. **Board as a distribution transform** — treat the board mathematically as a map from an input
   distribution to an output distribution:
   - funnel (drop-range) width vs. output standard deviation,
   - variance of the *input* distribution (e.g. Gaussian) vs. variance of the *output*.
6. **Brownian-motion framing** — treat vertical descent as time and horizontal motion as a 1-D
   random walk driven by peg impacts; study RMS displacement vs. board length.
7. **Variance convergence vs. bin resolution** — if variance is finite it should converge as bin
   resolution increases / ball count grows; otherwise it diverges — a fingerprint of
   CLT-violating (infinite-variance) behavior.
8. **Rigorous normality testing** — Q-Q plots with R² (linearity), skewness, kurtosis per
   configuration, rather than eyeballing histograms.

Secondary questions recorded in the notes: ball–ball interactions, finite-size ball/peg effects,
sand-vs-bead scaling, and the relationship between funnel size and grid proportionality.

### What is working today

- A fully **event-driven, analytic** simulation: no fixed time-step, no integration error.
  Collision times are found by solving polynomial equations exactly (quadratic for the
  detection line, linear for walls, quartic for pegs under gravity).
- A **parameter-sweep → animation-frame pipeline**: for each sweep value the engine emits a
  histogram, a Q-Q plot with normality metrics, a raw-data CSV, and a single-ball verification
  trajectory figure, all indexed by frame number.
- The GPU port is complete in structure: one CUDA thread per ball, whole frame = one kernel
  launch, with an in-kernel Durand–Kerner quartic solver replacing `np.roots`.
- Docker tooling for Windows + WSL2 with GPU passthrough, including smoke-test knobs
  (`GALTON_BALLS`, `GALTON_INTERVALS`).

### Known issue (blocking the GPU engine as committed)

`galton_cuda.py` declares the kernel with 16 parameters — the signature at
`galton_cuda.py:211-214` includes `step_counts, peg_tests` (apparent work-in-progress
instrumentation; `n_peg_tests` at line 227 is also computed but never stored) — but the only
launch site (`galton_cuda.py:392-396`) passes **14 arguments**. Numba will raise a
`TypeError` at the first kernel launch until the two dead parameters are removed from the
signature or the arrays are actually allocated and passed.

### What remains open (relative to the goals)

- The CLT-violation hunt (arcsine-law reproduction) — noted as a to-do, not started.
- Vibration / resonance experiments — not started; architecture-level change (moving pegs
  invalidate the prebuilt spatial grid).
- Ball–ball interactions — not started; breaks per-ball thread independence (would need a
  different parallelization strategy, e.g. batched time-stepping).
- Input-σ → output-σ relationship, Brownian RMS analysis, radial-parameter sweeps — planned,

## 4. How the GPU / CUDA Processing Is Handled

### Execution model

- **One GPU thread per ball.** The entire trajectory — the event loop, all three event
  solvers, the peg search, and the reflection math — runs *on the device*. A whole frame of
  `n_balls` trajectories is therefore a **single kernel launch**, replacing the sequential
  per-ball CPU loop of `galton_ultra.py`.
- Launch configuration: `threads_per_block = 256`, `blocks = ceil(n_balls / 256)`
  (`galton_cuda.py:388-389`). Threads beyond `n_balls` exit immediately.
- Work distribution is trivially parallel because balls do not interact — which is precisely
  why ball–ball interaction remains an open research item.

### The device-side quartic solver

`np.roots` does not exist inside CUDA kernels, so the time-to-peg-impact quartic is solved by
`_quartic_smallest_root` (`galton_cuda.py:114-206`) using **Durand–Kerner (Weierstrass)**
simultaneous complex iteration:

- The quartic is normalized to monic form; the four root estimates start at `(0.4+0.9j)^k`.
- Up to 40 iterations with quadratic convergence once roots separate; early exit when the max
  update step `< 1e-12` (typically converges in fewer than 15 steps).
- The four roots are held in **scalar locals (registers)**, deliberately *not*
  `cuda.local.array` — per the code comment, a local array would spill to per-thread local
  memory, which is latency-bound and "slows the kernel down by orders of magnitude at low
  occupancy".
- After iteration, roots with `|imag| < 1e-6` are accepted as real; the smallest one lying in
  the open interval `(t_lower, t_upper)` is returned, or `-1.0` if none. The upper bound is the
  current best collision time, so the search is progressively self-pruning.

### Per-batch data flow (`simulate_batch_cuda`, `galton_cuda.py:371-403`)

1. Host allocates device arrays and uploads inputs:
   `cuda.to_device` for `circles_centers`, `grid_data`, `grid_counts`, `x_inits`; device-side
   allocation for outputs `final_x` (float64) and `status` (int32).
2. One kernel launch; `cuda.synchronize()`; wall-clock timing printed per batch.
3. `final_x` and `status` are copied back to host NumPy arrays. That is the *entire* GPU↔CPU
   interface — two arrays per frame.

### What stays on the CPU and why

- Geometry generation and spatial-grid construction (cheap, once per frame).
- All rendering: histogram, Q-Q plot (pandas + scipy), and the single-ball **verification
  walk**, which re-simulates one random ball of the batch in pure Python with `np.roots` — a
  high-fidelity cross-check of the physics, and a visual diagnostic of what a trajectory looks
  like.
- The verification walk is capped at 500 steps; the GPU kernel at 1000 steps.

### Deviations from the CPU engine (documented in code comments)

- The CPU version's per-thread "seen pegs" dedup array is dropped on the GPU: re-testing a
  duplicate peg recomputes the same root, so the minimum is unchanged — dedup was a pure
  optimization, not a correctness requirement.
- All device math is **float64**.

## 5. Docker Assessment — Inefficiencies Found

The overall container architecture is sound (toolkit in image, driver from host via WSL2,
`--gpus all`, bind mount for outputs, clean `.dockerignore`). The following issues are real,
roughly in order of impact:

### D1. The `devel` image is several GB larger than needed

`nvidia/cuda:12.4.1-devel-ubuntu22.04` ships the *entire* toolkit — compilers, headers,
debuggers, Nsight profilers, static libraries (~5–7 GB uncompressed). Numba's CUDA JIT actually
needs only **NVVM (`libnvvm.so`) and `ptxas`** at kernel-compile time. The same functionality
fits in the much smaller `base` image plus two packages:

```dockerfile
FROM nvidia/cuda:12.4.1-base-ubuntu22.04
RUN apt-get update && apt-get install -y --no-install-recommends \
        cuda-nvcc-12-4 cuda-nvvm-12-4 ...
```

This cuts multiple GB from every pull/build and the on-disk footprint, with identical
simulation behavior.

### D2. Unpinned requirements — builds are non-reproducible, possibly broken

`requirements.txt` lists `numba` (and friends) with no version pins. Numba's CUDA target has
been split out of core Numba into the separate NVIDIA-maintained
[`numba-cuda`](https://pypi.org/project/numba-cuda/) package; `pip install numba` alone no
longer necessarily provides `numba.cuda` on recent versions. A rebuild today can therefore
produce an image where `from numba import cuda` fails at startup — silently breaking the
documented build command that used to work. **Fix:** pin exact versions (commit a
`pip freeze`), and add `numba-cuda` if the resolved numba requires it.

### D3. Ephemeral containers re-pay JIT and font-cache costs on every run

Runs use `--rm`, so two expensive caches are discarded each time:

- **Numba CUDA kernel compilation** — this large kernel is JIT-compiled through NVVM on every
  container start (a non-trivial fixed cost, noticeable relative to a 2000-ball frame).
  Remedy: set `NUMBA_CUDA_CACHE_DIR` (and/or `@cuda.jit(cache=True)`) pointing at a mounted
  volume, or bake a warmed cache into the image.
- **Matplotlib font cache** — rebuilt at first `savefig` on every fresh container. Remedy:
  mount/persist `~/.cache/matplotlib` similarly.

### D4. `python3-pip` apt package is redundant

The venv bootstraps its own pip via `ensurepip`; the distro pip is never used afterwards.
Dropping `python3-pip` from the apt install trims the image slightly.

### D5. `.dockerignore` misses `.git/`

Everything not ignored is uploaded to the daemon as build context on **every** build. The
`.git/` directory (and any generated GIFs) is not excluded, yet nothing is ever `COPY`ied from
it. Add `.git` and `*.gif`.

### D6. Small Dockerfile hygiene points (optional)

- Container runs as root; a `USER` directive would be better practice (no functional impact
  here).
- The `CMD` hard-codes `galton_cuda.py`; an `ENTRYPOINT` + args pattern would make smoke tests
  (`--env`-free) slightly cleaner. Cosmetic only.

### Adjacent runtime inefficiencies (not Docker, but they dominate wall-clock)

These are pipeline-level observations that dwarf the Docker overhead above:

- **Per-frame host→device re-upload of immutable data.** `simulate_batch_cuda` re-uploads
  `circles_centers`, `grid_data`, `grid_counts` on every batch — but in the currently
  configured `X_DROP_RANGE` sweep the peg geometry is *identical across all frames* (only the
  drop window changes). Device arrays could be created once per sweep and reused. (The grid is
  small — order 200 KB — so this is a cleanliness fix more than a speedup at 2 000 balls.)
- **The per-frame CPU verification walk is likely the slowest stage of each frame.** It
  re-simulates a full trajectory in pure Python, calling `np.roots` per collision. As a
  diagnostic it is valuable; for production sweeps it should be optional (e.g. env-gated
  `GALTON_VERIFY=0`).
- **float64 everywhere.** Consumer GeForce GPUs execute FP64 at 1/32–1/64 of FP32 throughput.
  If float32 accuracy proves sufficient (needs a validation run comparing distributions), the
  kernel would speed up dramatically on non-datacenter cards. With the current default of only
  2 000 balls × 10 frames the GPU is not the bottleneck; the port's value shows up at large N.
- **Frames are fully sequential.** GPU computation of frame *N+1* could overlap CPU rendering
  of frame *N* (double buffering) since they share no mutable state.
- **PNG writes cross the WSL2→Windows filesystem boundary** (9p/drvfs bind mount) at 300 dpi,
  three images per frame. Batching writes (render into the container filesystem, copy out at
  the end) or lowering dpi would speed up output-heavy sweeps.
- The Q-Q plot round-trips through the CSV on disk (`write → pandas.read_csv`) moments after
  the data was in memory — negligible cost, but it does double as a CSV integrity check.

### Already good (do not "fix")

- `apt-get update/install/rm -rf /var/lib/apt/lists` in a single `RUN` layer;
  `--no-install-recommends`.
- `requirements.txt` is `COPY`ied before `pip install`, so dependency layers cache correctly.
- The venv approach cleanly sidesteps PEP 668.
- `.dockerignore` otherwise excludes notebooks, figures, archived engines, and text files.
- Driver-on-host / toolkit-in-image split with `--gpus all` is the correct WSL2 architecture.

## 6. The Technical Pipeline, Precisely

This is the end-to-end control flow of `galton_cuda.py` per sweep frame. Default parameters
shown; `GALTON_BALLS` / `GALTON_INTERVALS` environment variables trim the run for smoke tests.

### Stage 0 — Sweep configuration (`__main__`, `galton_cuda.py:775-805`)

```
params = {
  N_FIRST_ROW: 51, N_ROWS: 50, DISTANCE: 2.0, H_INIT: 3.0, H_FINAL: 1.0,
  RADIUS: 0.7, X_DROP_RANGE: (-0.05, 0.05), WALL_PADDING: 0.5,
  COEFF_E: 0.1, CELL_SIZE: 2.0
}
SWEEP_PARAM = 'X_DROP_RANGE'; sweep_values = linspace(0.05, 47.0, 10)
```

For `X_DROP_RANGE`, each scalar sweep value `v` becomes the symmetric drop window `(-v, +v)`
(the "funnel width" experiment). CUDA availability is asserted up front with a clear error
message; `cuda.detect()` prints the device name.

### Stage 1 — Geometry generation (`generate_circle_geometry`)

Staggered (hexagonal) peg lattice:

- Row 0 has `N_FIRST_ROW = 51` pegs; odd rows have 50 (the stagger).
- Horizontal pitch `d = 2.0`; vertical pitch `d·√3/2 ≈ 1.732` (equilateral-triangle packing).
- Row 0 sits at `y = -H_INIT = -3.0`; each next row steps down by the vertical pitch.
- Every peg has radius `0.7` — which is also the **collision distance**: the quartic below
  fires when the ball *center* is 0.7 from a peg *center*, so the ball itself is currently a
  **point mass** (finite ball size is an open research item).
- Side walls are placed at `WALL_DISTANCE = max|x_center| + r + WALL_PADDING = 50 + 0.7 + 0.5 = 51.2`.
- Total pegs: 25 rows × 51 + 25 rows × 50 = **2 525**.

### Stage 2 — Spatial hashing (`build_spatial_grid`, host NumPy)

- Uniform grid with `cell_size = 2.0`; each peg is registered into **every cell its axis-aligned
  bounding box (`center ± radius`) overlaps**.
- Storage is dense and typed for the device: `grid_data[x_cell, y_cell, k]` = peg index or -1
  (int32, hard cap of 20 pegs per cell), `grid_counts[x_cell, y_cell]` = occupancy.
- Cell coordinates are offset by `(min_cx, min_cy)` so indices start at 0; lookups re-derive
  absolute cell indices and bounds-check against the grid extent.

### Stage 3 — Batch sampling

`n_balls = 2000` initial x positions drawn `~ Uniform(-v, +v)`; every ball starts at `y = 0`,
`vx = vy = 0` (dropped from rest above the peg field).

### Stage 4 — GPU kernel: event-driven trajectory integration

Each thread runs the following loop (max 1 000 iterations) for its ball, with
`g = 9.81` and detection line at `y_target = -H_INIT - N_ROWS·DISTANCE·cos30° - H_FINAL ≈ -90.60`:

1. **Time-to-detection-line** — solve `y_imp + vy·t − ½g·t² = y_target`, a quadratic in t;
   take the smallest root `> 1e-5`.
2. **Time-to-wall** — linear in t: left wall if `vx < 0`, right wall if `vx > 0`; root must
   exceed `1e-5`.
3. **Peg search** — compute the ball's motion bounding box over `[0, min(t_line, t_wall)]`
   (including the parabola's vertex if the apex falls inside the interval), expand it by the
   collision radius, and enumerate all grid cells the box overlaps. For every candidate peg,
   solve the **quartic** in t obtained from `|p(t) − c|² = radius²` with
   `p(t) = p₀ + v·t − ½g·t²ŷ` (coefficients `c4 = g²/4, c3 = −vy·g, c2 = vx²+vy²−dy·g,
   c1 = 2(dx·vx+dy·vy), c0 = dx²+dy²−r²`), keeping the smallest real root in
   `(1e-5, current best)` via the Durand–Kerner device solver.
4. **Earliest event wins** among {line, peg, wall}:
   - **Detection line (event 0):** record `final_x = x_next`, set `status = 1`, thread returns.
   - **Peg (event 1):** specular reflection with restitution `e = 0.1`:
     `v' = v − (1+e)(v·n̂)n̂` where `n̂` is the contact normal — the normal velocity component
     reverses scaled by `e`, the tangential component is preserved. The ball is then nudged
     `1e-4` outward along the normal so the next iteration cannot re-detect the same contact.
   - **Wall (event 2):** `vx → −e·vx`, `vy` unchanged, plus the same `1e-4` nudge.
5. If no event has a finite time, or the 1 000-step budget is exhausted, the ball is marked
   `status = 0` and `final_x = NaN` ("failed_or_out_of_bounds").

Note there is **no time-stepping anywhere**: between events the motion is the exact ballistic
parabola, so the only numerical artifacts are the root-finding tolerance (`1e-6` imaginary
part for "real", `1e-5` minimum time) and the post-collision nudges.

### Stage 5 — Results and analysis products (CPU)

For each frame index `XXX`:

| Artifact | File | Content |
|---|---|---|
| Raw data | `figures/galton_ball_positions_XXX.csv` | `ball_id, initial_x, final_x, status` for all 2 000 balls |
| Histogram | `figures/galton_distribution_XXX.png` | 200 bins over `[-51.2, 51.2]`, success count annotated, sweep parameter in the title |
| Verification walk | `figures/random_verification_path_XXX.png` | One random ball from the batch re-simulated in pure Python (`np.roots` quartics), trajectory drawn over the peg field, walls, and detection line |

Frames are produced sequentially for each sweep value; the file naming (zero-padded frame
index) is designed for later assembly into animations — the assembly step itself (ffmpeg /
ImageMagick) happens outside this repo.

### Physics summary

| Quantity | Value / rule |
|---|---|
| Gravity | 9.81 (units arbitrary, consistent) |
| Peg lattice | hexagonal, pitch 2.0, 51/50 alternating, 50 rows, 2 525 pegs |
| Collision distance (peg) | 0.7 from peg center (point-mass ball) |
| Restitution (pegs & walls) | e = 0.1 |
| Drop condition | from rest, y = 0, x ~ U(-v, v) |
| Detection line | y ≈ −90.60 (1 unit below the last row) |
| Numerical guards | t > 1e-5 per event; 1e-4 positional nudge after contacts |
| Step budgets | 1 000 (GPU kernel), 500 (CPU verification walk) |
